# LOT 0 — Préservation des fonctionnalités React

Les OpenAPI sont des contrats cibles de conception, pas une activation de nouveaux repositories. Cette matrice est une porte d’acceptation de chaque lot : un champ, un workflow ou un fichier non repris doit bloquer son basculement, jamais être supprimé silencieusement par l’adaptateur. Les schémas fermés seront affinés dans leur version de conception avant implémentation de chaque domaine ; leur présence ne prouve pas encore une parité fonctionnelle complète.

| Existant | Propriétaire / adaptation prévue |
| --- | --- |
| Clients, véhicule, adresses et données techniques | Clients. Conserver firstName/lastName, coordonnées, address et sections engine/transmission/tires/locksmith. L’adresse v2 couvre coordonnées géographiques, source et confirmation manuelle. Omission et null gardent leur sens explicite. |
| Documents `legacyProperties` | Stockage/import de maintenance contrôlé ; jamais propriété, permission ou relation. Classifier avant exposition à de nouveaux collègues. Ne pas supprimer les originaux même si la vue métier normale n’expose pas une propriété historique non classifiée. |
| Rendez-vous, statuts et horaires | Appointments. Le sélecteur de statut reste utilisable via une transition serveur valide. La version v1 du corps est transformée en If-Match uniquement dans l’adaptateur v2. Calendrier partagé et caches par entreprise ; pas de migration automatique des horaires concurrents. |
| Prestations, catégories, libellés FR/EN, mots-clés, tarification fixe/horaire/estimation | Interventions. Conserver les IDs chaîne existants ; versionner les prix. Tarifs appliqués conservés et calculés au serveur, sans remplacement par le tarif courant. |
| Diagnostic, réparation, temps, pièces, recommandations et historique véhicule | Interventions, avec commandes Inventory. Les champs opérationnels actuellement présents dans DocumentEditor deviennent des appels à Interventions ; Billing affiche l’instantané d’exécution autorisé. Le démarrage, la fin et l’annulation sont des commandes d’état, pas une modification arbitraire du coût ou du stock. |
| Produits | Inventory. SKU, nom, marque, références fabricant/OEM, code-barres, catégories/fournisseur et champs recherchés en SQL ; références alternatives, détails serrurier, photo/notes variables dans un document versionné ; compatibilités et historique de prix avec tables locales appropriées. Aucun lien fournisseur/catégorie uniquement dans JSON. |
| `Product.location` libre | Conserver comme indication historique (`data.storageHint`) ; ce texte ne devient pas arbitrairement une FK. `defaultLocationId` est un nouveau lien vérifié quand connu. |
| Quantités et réservations | Stock en milli-unités selon l’existant. Les quantités commerciales utilisent des chaînes décimales exactes : le code actuel accepte plus de trois décimales. Une conversion en stock non représentable est refusée, jamais arrondie en silence. |
| Anciens prix d’intervention en dollars, parfois sous le cent | Migration décimale exacte, conservation du ratio historique et du coût de ligne arrondi selon l’ancien calcul. Ne pas arrondir d’abord le prix unitaire ni remplacer une valeur inconnue par zéro. |
| Fournisseurs/achats/réceptions/retours | Inventory pour la réalité physique ; Accounting pour facture/règlement/avoir fournisseur. Un crédit financier ne refait pas le mouvement de retour physique. Les variantes de retour/crédit devront être contractées avant remplacement de cette partie de l’UI. |
| Soumissions, approbations, révisions, bons de travail, factures | Billing. Conserver numéros, versions approuvées et instantanés vendeur/client/véhicule/taxes. Les identifiants relationnels restent dans les colonnes SQL ; les instantanés ne sont pas des fiches courantes éditables. |
| Paiements clients, avoirs, remboursements | Billing, puis faits idempotents Accounting. Préserver paiements partiels, références uniques et absence de double crédit/consommation. |
| Factures fournisseurs/dépenses | Accounting. Préserver date du document, classification, ratios professionnel/éligibilité, références de preuve, liens d’achat/réception et taxes réellement retenues à la comptabilisation. Aucun défaut fiscal n’est inventé si une configuration manque. |
| Trésorerie, comptes, kilométrage, seuils/rapports fiscaux et clôtures | Accounting. Les variantes détaillées de rapports et de régularisation nécessitent leurs fixtures avant remplacement des écrans. Le rapport fiscal n’utilise pas le schéma d’une balance comptable. |
| Justificatifs IndexedDB, logo et fichiers historiques | Paquet fichiers + manifeste + empreintes ; stockage privé du service propriétaire et métadonnées SQL. Les téléchargements v2 utilisent fetch authentifié avec le contexte d’entreprise, puis blob local ; une ancre sans header d’entreprise ne crée pas un accès de secours. |
| Paramètres | Façade Settings conservée : horaires Appointments, catalogue/prix Interventions, profil commercial et numérotation Billing, fiscalité Accounting. Anciennes valeurs conservées dans la sauvegarde avant toute répartition. |
| Langue et préférences personnelles | Peuvent rester locales, sans devenir une preuve d’accès ou une donnée métier commune. |

## Compatibilité stricte

Les référentiels livrés dans le code (catégories ou prestations prédéfinies) sont des modèles immuables, pas un stock ou un tarif commun aux entreprises. Leur adoption crée explicitement des lignes de catalogue d’entreprise. Les codes naturels réutilisables sont uniques par entreprise ; les FK composites incluent ce périmètre. Les identifiants historiques manquants demandent une clé de correspondance approuvée, pas un faux identifiant présenté comme existant.

Les états des rendez-vous/interventions et les variantes d’approbation, retour, crédit et correction doivent être décrits par des matrices de transition testées avant leur lot. Les endpoints d’action empêchent qu’un PATCH de brouillon clôture une intervention ou émette une facture sans les contrôles associés. Aucune ancienne route v1 ne change dans le lot 0.

Le serveur est autoritaire sur les montants, le stock, les permissions et les transitions. React peut conserver ses calculs de prévisualisation et ses fonctions d’impression, à comparer aux résultats serveur ; il ne corrige pas silencieusement un résultat différent. Les champs financiers masqués par permission restent absents/indisponibles, jamais transformés en prix zéro. Conserver FR/EN et les messages distincts d’expiration, interdiction, conflit et indisponibilité.

Les identités d’entreprise, rôles et réglages réels initiaux restent des décisions à approuver. Aucun composant, fichier localStorage, fichier IndexedDB ou environnement A/B n’est modifié par cette matrice.
